# Потоки данных сессий: дизайн

Дата: 2026-08-10. Затрагивает два репозитория: `ccfzf` (писатель) и
`windows11-manager` (`src/claude-wt`, читатель). В `ccfzf-picker` правок нет.

## Задача

Фоновая нагрузка двух долгоживущих процессов на Windows и посекундный расход на
pc-virt. Причина названа неверно с самого начала — «дамп на 184 КБ большой», —
и замеры это опровергли: файл читается за 0.92 мс и разбирается за 0.32 мс.
Платится за другое.

### Что померено

**Сторона Windows**, одно перечитывание индекса:

| операция | цена |
|---|---|
| `readFileSync` 184 КБ с `V:` | 0.92 мс |
| `JSON.parse` тех же байт | 0.32 мс |
| `openSync r+` (слом read lease SMB) | 0.04 мс |
| `indexSessions` без обращений к диску | 0.6 мс |
| **`indexSessions` как есть** | **455 мс** |

Разница — 354 сетевых `statSync` по 1.3 мс: `activityAt()`
(`windows11-manager/src/claude-wt/progress.js:105`)
берёт mtime `<id>.state.json` на `V:`, разрешая тёзок по заголовку. На 200
сессий приходится 98 уникальных заголовков, 119 сессий сидят на 17 общих —
один и тот же проект, открытый заново десятки раз за недели. Комментарий над
`activityAt` обещает «обычно ни разу за тик»; замысел был верен для списка, где
дубликатов единицы. Вызовов 354 на 200 сессий — внутри одной сборки один id
статится по нескольку раз, памяти между группами нет.

Живых сессий при этом 6 из 200, с открытым окном — 5. Полсекунды тратятся на
выяснение, какая из двадцати одной давно закрытой «ExpertizeMe» свежее.

Умножая на потребителей (по 4 перечитывания в минуту в каждом из двух
процессов): демон `claude-wt` — ~3.4% ядра и ~84 МБ мусора в час, MQTT-процесс —
~2.3% и ~69 МБ. Плюс 2 мс на каждый тик демона: `progressStamp()` статит каталог
на `V:` раз в секунду только чтобы спросить «не менялось ли».

**Сторона pc-virt**, до сих пор не меренная. `ccfzf --state` — 320 мс CPU и
286 090 байт на вызов, а пикер зовёт его **раз в секунду**, пока открыт, и
каждый раз новым процессом через ssh: кэша между вызовами нет вовсе. Профиль:

| | |
|---|---|
| `head_gist` ×200 | **165 мс** (42%) |
| `tail_facts` ×200 | **117 мс** (30%) |
| всё остальное | ~40 мс |

`head_gist` ищет первый промпт сессии — величину неизменную. `tail_facts`
меняется только вместе с mtime транскрипта. То есть 280 из 320 мс — пересчёт
того, что не менялось, двести раз в секунду.

Состав ответа по полям (байты): `agent` 71.6 КБ, `doing` 52.6 КБ, `gist`
33.6 КБ, `file` 23.5 КБ (выводится из `cwd` и `id`), `projects` 9.1 КБ, `cwd`
8.7 КБ, `id` 7.6 КБ.

## Решения

Четыре правки. Ни одна не трогает разрешение тёзок по существу — меняется
только то, откуда берётся число, по которому их сравнивают.

### A. `activityAt` едет в дампе, а не добывается по сети

Файлы `<id>.state.json`, которые читатель статит через `V:`, у ccfzf
**локальные**, и он их уже обходит: `hook_stamps()` (ccfzf:696) отдаёт
`{sid: mtime}` одним `scandir`, за доли миллисекунды. Число посчитано на
pc-virt и просто не доезжает.

**ccfzf.** Звать `hook_stamps()` в режимах `dump` и `state` (ещё один scandir
по ~440 записям) и класть в запись сессии `"activityAt": int(stamps.get(sid, 0))`.
Ноль значит «хук про эту сессию не писал» — то же, что возвращает сегодняшний
сетевой вызов при отсутствии файла. Единица та же: epoch-секунды, `floor` от
mtime. Сравнение не меняется ни на бит.

Альтернатива — вернуть `stamps` четвёртым элементом из `running_sessions()`,
которая её уже зовёт. Отвергнута: смена арности трогает все места вызова ради
0.3 мс.

**windows11-manager.** `byActivityThen` начинает принимать функцию от *сессии*,
а не от id, и берёт `s.activityAt`, когда поле есть. Сеть не трогается вовсе.
354 → 0.

**Побочное: `progressStamp` уходит из ключа кэша.** Он там стоит ровно потому,
что индекс зависит от отметок хуков помимо дампа. С полем в дампе этой
зависимости нет, и посекундный сетевой stat каталога исчезает. Считать его
только тогда, когда прошлый прочитанный дамп поля не нёс: `loadDump` знает это
после разбора и запоминает флагом в записи кэша. Первое чтение после старта
процесса платит один stat, дальше — ноль.

**Что меняется по свежести.** Сейчас `activityAt` свежий, а список кандидатов
из дампа — до 30 с старый (`STATE_DUMP_MAX_AGE`) плюс 15 с кэша индекса.
Станет — обе половины одного возраста. Это не ухудшение, а устранение
расхождения: ранжировать свежими отметками устаревший список смысла не было.
Когда пикер закрыт и дамп не переписывается вовсе, разрешать нечего — новой
сессии в дампе просто нет, и это ограничение существует независимо от правки.

**Fallback: поля нет.** Старый ccfzf, откат, окно рассинхрона между двумя
независимыми деплоями. Сетевой путь остаётся, но с двумя стражами:

1. *Памятка на одну сборку индекса.* Один id статится один раз, а не по
   нескольку. 354 → максимум 200. Чистая арифметика, результат тот же.
2. *Предфильтр по `mtime` из самого дампа.* Хук пишет на тот же вызов
   инструмента, что и транскрипт, — отметки расходятся меньше чем на секунду
   (замерено 2026-08-06, докстринг `hook_stamps`: 0.3 с и 0.7 с). Значит
   кандидат, чей `mtime` отстал от лучшего в группе больше чем на
   `HOOK_SKEW_MS` (5 минут — запас на длинный вызов инструмента, внутри
   которого хук уже отметился, а транскрипт ещё нет), выиграть по хуку не
   может, и статить его незачем. Двадцать одна мёртвая
   «ExpertizeMe» отваливается без единого обращения к сети. Когда после отсева
   остался один кандидат — сеть не трогается совсем.

   Отсев опирается на то, что транскрипт пишет только работающая сессия:
   свежий `mtime` — сам по себе признак недавней активности, и кандидат,
   отставший по нему, отстал и по хуку. Опорой берётся самый свежий `mtime` в
   группе, а не «сейчас»: часы двух машин сравнивать не приходится вовсе.

В худшем случае это 0–8 вызовов вместо 354, и поведение не меняется нигде:
отсеиваются только те, кто и так проигрывал.

### B. Дамп — канал к трекеру, а не общий снимок

Комментарий над режимом `dump` объявляет его «everything ccfzf can see, for
whatever else wants to know it». По факту читателей два, оба в
`windows11-manager/src/claude-wt/sessions.js` (`loadSessionIndex`,
`loadBackgroundAgents`), и оба смотрят в 7 полей из 13. Пикер сюда не ходит
вовсе — он берёт `--state` по ssh. Считаем файл тем, чем он стал.

**Поля.** `keep` в режиме `state` и запись в режиме `dump` становятся одним
списком:

```
id, title, cwd, live, mtime, kind, parent, activityAt
```

Уходят `file`, `projects`, `gist`, `doing`, `age`, `frozen` — сверено по обоим
читателям, не используется ни одно.

**Форма у двух писателей одна.** Сегодня `dump` пишет богаче, чем `state`, —
два писателя одного файла с разным содержимым, и расхождение уже стоит
отдельного комментария (ccfzf:1282). Обе ветки пишут одну проекцию.

**Срез.** Новейшие `--limit` штук **∪ все `live` ∪ все с окном**. Объединение —
не перестраховка, а гарантия: ни одна сессия, способная владеть окном, не
выпадает, и фильтровать по `live` (флаг уже врал — 2026-08-01, работающая
сессия с `live: false`) при этом не приходится, `live` только добавляет.

Порядок в файле сохраняется по `mtime`, как сейчас.

Ожидаемо: 184 КБ → ~25 КБ. Читателям править нечего — все семь используемых
полей на месте.

**Остаточный риск, названный вслух.** Окно, открытое на сессии, чей транскрипт
не трогали дольше, чем покрывает срез (при `--limit 100` — 7.4 дня на этой
машине), **и** файл оконного трекера в этот момент протух по `WINDOWS_TTL`
(иначе объединение её подберёт). Лечится поднятием `--limit`.

### C. Памятка фактов в ccfzf

`--state` запускается новым процессом на каждый опрос, поэтому памятка нужна на
диске, а не в памяти.

**Файл.** `~/.cache/ccfzf/facts.json` (`$XDG_CACHE_HOME`, если задан).
Отключается пустым `CCFZF_FACTS_FILE`.

**Форма.** `{"v": 1, "files": {<path>: {mtime, size, title, doing, gist, gistDone}}}`

**Правило.** Попадание по паре `(mtime, size)` — `title` и `doing` берутся
готовыми. Промах — считаются `tail_facts` и записываются.

**`gist` живёт по своему правилу, и это главный выигрыш.** Первый промпт сессии
неизменен. Ключевать его по `mtime` незачем: найденный непустой `gist`
переносится через любые изменения файла, и `head_gist` не зовётся больше
никогда. Это 165 мс из 320, и уходят они даже у сессий, которые пишутся прямо
сейчас. Пустой `gist` пересчитывается, пока `size <= HEAD_LIMIT`; за этим
порогом ответ измениться уже не может (`head_gist` дальше и не смотрит) — тогда
ставится `gistDone: true` и попытки прекращаются.

**Запись.** Атомарно (tmp + rename, как `write_json`) и только при изменениях.
Записи файлов, выпавших из текущего списка, вычищаются — иначе памятка растёт
на каждую когда-либо виденную сессию.

**Гонка.** Два ccfzf могут писать памятку одновременно (пикер опрашивает раз в
секунду, `--dump` от windows-mqtt может лечь рядом). Последний победил, и это
верно: памятка — чистая функция от содержимого файлов, у двух писателей
расходиться нечему.

**Про SMB здесь говорить нечего, и это надо записать в комментарий.** Каталог
локальный, ext4; весь шрам с врущим `mtime` — про чтение `V:` с Windows.
Следующий читатель кода иначе потратит время на тот же вопрос.

Ожидаемо: 1–3 промаха на вызов, 320 мс → ~40 мс. Памятка при `--limit 100` —
около 45 КБ, разбор ~0.15 мс.

### D. `--limit N`, по умолчанию 100

Заменяет константу `DUMP_SESSIONS = 200` и управляет **всем сразу**: сколько
новейших сессий ccfzf вообще рассматривает — и в `--state`, и в `--dump`. Один
ключ вместо двух чисел, и вдвое меньше хвостов на холодной памятке.

Разбор — в общем `while (($#))`, рядом с `--session`, обе формы (`--limit N` и
`--limit=N`), значение проверяется на целое положительное, иначе `exit 2`.
Уезжает в python дополнительным argv у режимов `state` и `dump`.

Срез `--limit` покрывает 7.4 дня на этой машине (200 сессий — 13.1 дня), при
том что все живые и оконные сессии сидят в первых 11 по `mtime`.

**Осознанный отказ.** Пикер зовёт `ccfzf --state` жёсткой строкой
(`ccfzf-picker/src-tauri/src/state_source.rs:32`), так что после правки он
получит 100 сессий, и попросить больше будет нечем без нового ключа в
`config.yaml`. Ключ не заводим, пока не понадобится: вся задача — про то, что
мёртвого груза слишком много, и первый же шаг обратно противоречил бы ей.

## Контракт дампа после правки

```json
{
  "generated": 1770000000.0,
  "total": 819,
  "shown": 104,
  "sessions": [
    {"id": "…", "title": "…", "cwd": "/home/…", "live": true,
     "mtime": 1770000000.0, "kind": "interactive", "parent": "",
     "activityAt": 1769999998}
  ]
}
```

`total` — сколько сессий видно всего (как сейчас), `shown` — сколько записано
после среза и объединения.

## Тесты

**ccfzf** (`tests/`, pytest поверх `harness.py`):

- `--limit` разбирается в обеих формах; отрицательное и нечисловое → `exit 2`;
  умолчание 100.
- Дамп несёт ровно восемь полей и не несёт `gist`/`doing`/`file`.
- `activityAt` берётся из mtime `<id>.state.json`; сессия без файла хука
  получает 0.
- Срез: сессия `live` вне первых N в дампе есть; сессия с окном вне первых N в
  дампе есть; мёртвая вне первых N — нет.
- Памятка: попадание по `(mtime, size)` не зовёт `tail_facts`; изменение файла
  зовёт; непустой `gist` переживает изменение файла и не зовёт `head_gist`;
  пустой `gist` у файла больше `HEAD_LIMIT` получает `gistDone` и больше не
  пересчитывается; выпавшая из списка запись вычищается; битая памятка
  (порванный json, чужая `v`) не роняет вызов, а считается пустой.

**windows11-manager** (`node --test`):

- `indexSessions` предпочитает `s.activityAt` и не зовёт сетевую функцию вовсе,
  когда поле есть у всех кандидатов.
- Fallback: функция зовётся не больше одного раза на id за сборку.
- Fallback: кандидат, отставший по `mtime` больше `HOOK_SKEW_MS`, не статится.
- Fallback: единственный кандидат после отсева не статится.
- `loadDump` не зовёт `progressStamp`, когда дамп нёс `activityAt`; зовёт,
  когда не нёс.
- Смешанный дамп (часть сессий с полем, часть без) сравнивается корректно.

## Порядок выкатки

C ни от чего не зависит и может ехать первым. A и B — по коммиту в каждый
репозиторий; **читателя выкатывать первым**: он переживает дамп без
`activityAt` (fallback), а обратный порядок оставил бы старого читателя со
старой ценой, но не сломал бы его.

Деплой после завершения — windows-mqtt на Windows, `npm run deploy-fast`
(правка только в node-части `windows11-manager`). Помнить про две молчащие
ловушки `deploy-fast` через `ssh popstas-pc`: джанкшен `node_modules\windows11-manager`
сетевому логону не виден и правка не едет (обход — прямой `xcopy` каталога
`src`), а `cmd /c start` из того же логона до рабочего стола не доходит
(поднимать временной задачей `schtasks`, проверять
`tasklist /FI "IMAGENAME eq windows-mqtt.exe" /FO CSV` — должен быть `Console`,
сессия 1). Правка в ccfzf живёт на pc-virt и деплоя не требует.

## Чего не делаем

- **Долгий канал `ccfzf --serve`.** Быстрее памятки, но это новый демон, новые
  режимы отказа и переподключения ради последних ~40 мс.
- **Условный ответ `--state --if-changed <fp>`.** Убрал бы 286 КБ на опрос, но
  требует правки в третьем репозитории; отложено до отдельного захода.
- **Фильтрация дампа по `live`.** Отвергнута по существу: флаг уже врал, и
  ставить привязку окна в зависимость от эвристики — тот самый баг ещё раз.
  Срез идёт по `mtime` и только добавляет `live`, не убавляет.
- **Ключ `limit` в конфиге пикера.** См. D.
